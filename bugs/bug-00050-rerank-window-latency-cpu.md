# bug-00050 重排窗口放大到 50 后检索 CPU / 延迟线性放大并超预算（窗口档位无上限护栏）

## 现象（A018 验收反馈）

- 启用态 = `mcp-server/sango/.env` 设 `SANGO_RERANKER=on` + A030 锁定档位（截断 128 / batch 16 / intra 8）。
- 把 `SANGO_RERANKER_WINDOW` 由 20 改为 50 后本机 CPU 飙升、检索明显变慢，同时观察到内存占用上涨。
- 负责人猜测：BM25 可能召回 1700-2000 条候选、全部进了重排。

## 实测（2026-09-29，Coco；现网 dist + 真实权重 + 真语料，零 LLM 调用）

同机 AMD Ryzen 7 5800H（8 核 16 线程）/ 27.9GB；定点四题（华雄 典故#1、拒答#5；刘备 问法归一#4、事件关系#10）× 3 轮 = 12 次采样；档位固定 128/16/8，仅改窗口。

| 读数 | 窗口 20 | 窗口 50 |
|------|---------|---------|
| 检索总耗时 P50 / max | 877.9ms / 930.6ms | 2117.8ms / 2303.4ms |
| 重排段 `timing.rerank` P50 | 794.9ms | 2011.5ms |
| `rerank.considered`（真正进 cross-encoder 的条数） | 19-20 | 49-50 |
| 三路合并候选池 `funnel.mergedCandidates` | 1806 ~ 2300（与窗口无关） | 同 |
| 单查询 CPU 时间（`process.cpuUsage` ÷ 12） | 8141ms | 17589ms |
| 进程 RSS（整批跑完） | 2385.7MB | 2390.3MB |

同进程内存分段：

| 阶段 | RSS |
|------|-----|
| 进程启动 | 57.8MB |
| 语料 + 索引加载（无模型） | 265.2MB |
| 首次向量检索（BGE-M3 编码器加载） | 1603.6MB |
| 首调重排（cross-encoder 权重 + ORT 工作区） | 2354.9MB |
| 窗口 20 批量后 | 2385.7MB |
| 窗口 50 批量后 | 2390.3MB |

## 结论

1. **「参与重排的数据过多」不成立**：进 cross-encoder 的条数 = 窗口条数（`considered` 19-20 / 49-50）。词法召回池确实是 1806~2300 条（负责人对量级的猜测正确），但它们只参与规则加权打分与排序，不进重排——窗口截断发生在 `rerankWindow()` 的 `pool.slice(0, windowSize)`（`mcp-server/sango/src/search/sango-index.ts:1001`）。
2. **成本线性于窗口，这才是「CPU 飙升」的来源**：本档位单条推理 ≈ 39-40ms；窗口 20→50 即 2.5×，重排段 795ms→2011ms，单查询 CPU 时间 8.1s→17.6s（增量 ≈ 重排段墙钟 +1.2s × 8 线程，8 线程接近满载约 2.2s/次）。
3. **内存不随窗口变化**（RSS +4.6MB，噪声级）。内存跃升来自「开重排」本身：cross-encoder 常驻 +751MB；另 BGE-M3 编码器 +1338MB（无重排同样加载，与重排无关）。负责人把「开重排的常驻增长」与「改窗口」一起观察到，内存部分不能归因于窗口。
4. **超预算**：窗口 50 时重排段 P50 2011ms，已超 A030 验收 5「重排阶段 P95 ≤ 1000ms」口径（`requirements/feat-A030-reranker.md:38`，负责人 2026-09-28 拍板）2 倍；窗口 20 时 P50 795ms、P95 787-930ms 达标。
5. **代码层结构性隐患（顺带登记）**：`rerankWindowSize()`（`sango-index.ts:74-77`）只校验 ≥1，无上限、无预算联动护栏，配置可任意放大而不报成本；非事件路径合并池无上限（`capMergedPool` 仅在事件路 `l1l2Groups.length > 0` 时调用，`sango-index.ts:751-761`），实测池 1806~2300 条。量级小（多 2300 个对象排序 / 构造），非本现象根因。

## 影响

- 窗口 >20 在生产延迟预算内不可用（P50 已超 2×）；单次检索占满 8 线程约 2.2s，并发即雪崩。
- 负责人观察到的「top21-50 未参与重排 → 召回质量上不来」是窗口口径的固有限制，不是代码缺陷；扩窗口的质量收益与延迟成本需一并拍板。

- 器坊当前 6 个实例（2 个 dist + 4 个 src），其中 2 个 dist 都能吃重排权重：前厅评测页是内存再上台阶的现成第二条路径。

## 轻量重排模型候选（窗口 50 进预算的选型归因）

- 预算换算：P95 ≤ 1000ms / 50 条 → ≤20ms/条；现用 int8 BAAI/bge-reranker-base 实测 ≈39-40ms/条 → 需再快 ≈2×。
- 同线无更轻档：bge-reranker-base（278M，12 层/768）已是 BGE 重排线最轻档，上档 v2-m3 568M 更重。
- 跨线候选 cross-encoder/mmarco-mMiniLMv2-L12-H384-v1（多语 ≈118M）：预估 ≈15-20ms/条 → 窗口 50 约 750-1000ms，刚压线。代价：中文/文言质量未验证；BERT 系分词器带 token_type_ids，需改 pair 拼装口径并重导 ONNX，非改配置即可换。
- 不可用 / 不合：英文 MiniLM 档（22-33M，7-12ms）中文不可用；Qwen3-Reranker-0.6B（600M）比现用更重，与「兼顾配置」相悖。
- 不换模型的杠杆：截断 128→64（省约 40%，仍不进预算）、级联粗筛 50→20、ORT 走 DirectML 核显、按 query 缓存。
- 前置门槛（未验证）：窗口 50 是否有质量收益——A030 池覆盖探针 / 标准集读数缺失；若 top21-50 不含金标，换模型扩窗口为纯成本。
## 待办（负责人拍板）

1. A 案（推荐，最小）：给窗口加护栏——设上限 + 首调按实测单条成本告警「窗口 N ≈ N×40ms，预算 P95 1000ms → 建议 ≤20」，口径写进 A030 需求（窗口上限与延迟预算绑定）。代价：放弃窗口 >20 的召回收益（预算内本就放不下）。
2. B 案：换更快打分器（更小 cross-encoder / 量化 v2 类）或 GPU，使窗口 50 进预算。代价：属 A030 未跑完的选型归因，工期长。
3. C 案：不扩窗口，用结构路（事件桥 / 标签锚点）补 top21-50 召回缺口（A018 已落地方向，零新增推理）。代价：覆盖有限，效果需评测。
4. 顺带：非事件路径合并池加上限（与事件路同为 120 口径）——低风险收口。
5. 环境侧（零代码、非本票修复）：收口冗余实例——4 个 sango src 留 1、4 个 weather 留 1、不用时关 8787 评测实例，省 ≈1.3GB 且少 4 个抢核进程；VSCode 只留必要窗口。
