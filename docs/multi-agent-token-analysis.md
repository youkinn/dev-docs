## Q1 · 负责人发消息时，Coco 依次加载哪些全局内容

固定前缀 ≈ 8.5~9k token（每轮重发，但 96% 命中缓存）：

| 序 | 加载项 | 说明 | 估算 |
|---|---|---|---|
| 1 | 系统提示词骨架 | 协作模式、沙箱/权限规则、环境上下文（cwd/日期/时区/文件系统根） | ~1-1.5k |
| 2 | 工具定义 schema | exec_command / write_stdin / web_search / view_image 等 | ~3-4k |
| 3 | skills 清单 | 所有 skill 的 name+description 全局注入；完整正文按需加载 | ~0.3k |
| 4 | 项目 AGENTS.md | 从工作目录向上找最近层级（dev-docs） | ~2.7k |
| 5 | 对话历史 | 之前轮次（缓存命中主体） | 随会话增长 |
| 6 | 最新消息 | 每轮唯一"新鲜"部分 | 每次几百 |

要点：
- 全局 config.toml（445B）只影响行为，不进上下文。
- 全局 `~/.codex/AGENTS.md` 为空；无全局 instructions。
- skill 完整正文按需加载：ponytail ~1.7k / token-saver ~2.4k（自动触发时是每请求固定开销）。

## Q2 · 多 Agent 协同，通用需求怎么传？是否只有一份

- 存储只有一份：`requirements/feat-XXX.md`（Coco 与负责人定稿，全员阅读）。
- 运行时摘要会复制 N 份：Coco 把"公共需求要点"压缩成 300~600 token 塞进每个子代理 spawn prompt（`fork_context=false` 隔离主会话历史），子代理不重读同一文件。
- 各项目 AGENTS.md（mcp-server ~135 / mcp-web ~610 / mcp-orchestrator ~850 token）只管各自项目规则，不参与团队约定共享。

## Q3 · 怎么知道子代理完成？他们回报什么

- 机制：spawn 后阻塞式一次性等待（2-5 分钟长超时），禁止轮询。
- 回报：结构化摘要三件套——产出 / 关键决策 / 未解决问题 + 分支名；禁止返回原始文件内容。
- Coco 拿到摘要后，用一轮 exec 拉全量 diff 做终审，通过才进合并流程。

## Q4 · 一次需求全流程 Token 分布（估算）

主会话新增 token，小~中型功能：

| 阶段 | 新增 token | 备注 |
|---|---|---|
| 需求对接（负责人↔Coco 对话） | ~10-30k | 每轮固定前缀 8.5k（96% 缓存）+ 新消息；轮数越多越贵 |
| 文档定稿（需求/接口/索引） | ~3-8k | 写 2000-4000 字 + 读模板 |
| 建分支 / 提交 / PR | ~1-2k | git 操作便宜 |
| spawn 子代理 | ~1-2k（主会话） | 子代理 token 在轻量模型独立会话，不占主会话 如尝试3次仍无法分配，可继承父模型。但要明确告知情况 |
| 审查（拉全量 diff） | ~20-60k | 3 仓库 diff 全进主会话，最大单块 |
| 验收 + 合并记录 | ~3-10k | 输出截断则可控 |
| 合计 | ~40-110k | 视功能大小 |

结论：**最耗 token 的是审查阶段**（全量 diff 进主会话）；需求对接排第二（轮次太多会反超）。

通用上下文占比（两个口径）：
- 按发送字节口径：通用前缀 8.5k × ~30 轮 ≈ 255k，占发送总量 >90%——但 96% 命中缓存，按缓存价很便宜。
- 按新增（未命中）token 口径：通用上下文只在会话开头加载一次 ≈ 8.5k，占全程新增（40-110k）的 ~8-15%。

结论：通用上下文不是主矛盾；真正吃 token 的是审查 diff 与对话轮次。

## Q5 · 对策清单

落地状态（2026-09-15）：①③④ 已写入 `AGENTS.md` 协作流程；② 已有规则覆盖（Token 控制 #5 阶段分隔 /compact）；⑤⑥ 保留为建议。

1. **审查瘦身**（已入流程）——子代理摘要加"变更文件清单 + 每文件行数"；审查先 `git diff --stat` 概览，再按需拉具体文件/hunk，禁止全量 diff 进上下文。
2. 需求对接瘦身（已有规则覆盖）——要点一次写进需求文档，少来回；>10 轮即 /compact 或开新会话。
3. **子代理自查前置**（已入流程）——先跑测试/lint 通过再提交，减少打回往返。
4. **PR 粒度**（已入流程，并入①）——保持单次 diff 小，审查成本随 diff 线性降。
5. 技能正文（保留建议）——ponytail/token-saver 高频触发时可精简正文。
6. 缓存友好（保留建议）——多条问题合并成一条发，避免刷屏式小轮次。

## 附：职责边界（2026-09-16 决策）

- 多人同项目开发：先建本次需求分支，成员基于它拉个人分支。
- 往需求分支合入：成员自己直接合（不经过 PR、无需 Coco）。
- 验收：由负责人在需求分支上完成（Coco 不再跑集成测试，控 token）；验收通过后才由 Coco 向 main 发起 PR。
- 合并：由负责人执行（成员不直接操作 main）。
