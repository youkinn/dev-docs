# Bug 对接流程（负责人 → Coco）

> 用途：负责人说「我发现一个 bug」之后的固定动作：**先问清特性 → 查两处（特性需求文档 / Bug 索引）→ 排查定位 → 定性报票**。
> 配合：`docs/troubleshooting.md`（**问题排查手册**，管「怎么定位」）；本文件管「怎么对接、怎么登记」。
> 依据：`AGENTS.md`（编号与 Commit / Bug 登记从简 / 分支与合并）、`bugs/INDEX.md`、`requirements/`。
> 一句话：**bug 一定挂在某个特性下；先问特性，再查两处，最后才谈怎么修。**

## 1. 触发与第一件事：先问清特性

负责人开场（示例）：

```text
Coco，我发现一个 bug：<现象>
```

**我必须先问清**（不猜、不跳过）：

| 必问 | 为什么 |
|------|--------|
| **属于哪个特性**（`feat-AXXX`） | 决定去哪份需求文档核对「是不是缺陷」、bug 关联到哪个特性、走哪条分支策略 |
| 现象（用户看到什么） | 排查与验收的对象 |
| 复现方式 / traceId | 定位入口；没有 traceId 时按排查手册「命令速查」的「C. 反查」找 |

> 负责人只说「我发现一个 bug」而没说特性 → **我先问特性，再动手**。

## 2. 第一时间查两处

### 2.1 特性需求文档 —— 判断「是不是缺陷」

路径：`requirements/feat-AXXX-*.md`（先按 `requirements/INDEX.md` 定位文件名）。重点看四处：

| 看哪里 | 结论 |
|--------|------|
| 验收标准 | 现象**不符合验收标准** → 是缺陷 |
| 目标 | 现象使目标无法达成 → 是缺陷 |
| 非目标（本次不做） | 现象正是「非目标」→ **不是缺陷**，是需求变更 → 走 `docs/requirement-intake.md` |
| 风险 & 开放问题 | 已写明的已知风险 → 先与负责人确认口径，别当新缺陷报 |

需求文档没写清楚 → 先补需求口径再判（属需求描述缺口，不是代码 bug）。

### 2.2 Bug 索引 —— 判断「是不是已登记」

路径：`bugs/INDEX.md`（登记在案的全部 bug）

| 查到 | 动作 |
|------|------|
| 没登记 | 按第 4 节定性后新开票 |
| 已登记 · 待修复 | **不新开票**；把本次现象 / traceId / 读数补进既有条目（或对应 bug 文档） |
| 已登记 · 修复中 | 同上，不重复派活 |
| 已登记 · 已修复 | 属**回归**（修复后又出现）→ 新开票并在标题注明「回归」，不复用旧号 |

## 3. 定位（交给排查手册）

按 `docs/troubleshooting.md` 走：步骤 1 概览 → 步骤 2 失败面 → 步骤 3 耗时归因 → 步骤 4 / 5 明细 → 步骤 6 检索诊断 → 步骤 7 路由核对；结论登记到 `docs/troubleshooting-notes.md` 的「已排查 trace 索引」。

## 4. 定性 → 报票 → 登记

- **定性以需求文档为准**（排查手册「怎么判」）
- 报票：我发行 `bug-{五位数字}`（按 `bugs/INDEX.md` 自增、不可重用）
- 登记从简（2026-09-21 决策）：
  - 小 bug（根因显然、改动一两行）→ 只在 `bugs/INDEX.md` 登记一行（标题写清现象 + 根因要点 + 修复口径）
  - 长期课题 / 需承载排查过程 · 根因分析 · 复现数据 · 契约变更 → 建 `bugs/bug-XXXXX-<描述>.md`
- INDEX 行格式：`| Bug 号 | 标题 | 涉及项目 | 关联特性 | 状态 | 修复日期 |`
- 状态流转：`待修复`（已登记未分配）→ `修复中`（已分配开发中）→ `已修复`（代码已合并）；修复日期在合并后回填（`AGENTS.md` 第 10 条）
- 指派按层（排查手册「定层 → 定人」）：前端 小叶 / 编排 小胡 / Transport · Server 老陈

## 5. 分支与合并（按阶段）

| 阶段 | 策略 |
|------|------|
| 已上线部分 | 一票一分支 `{owner}/bug-XXXXX_<描述>`：独立提交 → 提测 → 负责人验收 → 通过后我发起 PR → 负责人合并 → 我自动收尾登记 |
| 开发阶段（未上线） | 多个 bug 在同一分支以 `#bug-XXXXX fix:` 提交堆积，随批次提测 / 验收 / 合并 |

## 6. 我产出什么（一次 bug 对接的交付物）

| 步骤 | 产出 |
|------|------|
| 1 | 问清结果：特性号 + 现象 + 复现材料（缺什么明确列出） |
| 2 | 两处查证结论：需求文档里怎么说 / INDEX 里有没有 |
| 3 | 排查结论：现象 + 根因层 + 证据读数 + 后续动作 |
| 4 | bug 号 + 登记（INDEX 行或 bug 文档）+ 指派 + 分支 |
| 5 | 提测 / 合并后：状态与修复日期回填 |

## 7. 边界与红线

- 无票不动代码；Coco 不改业务代码（第 1、3 条）
- 归档需求文档冻结：bug **不回填**需求文档，只走 `bugs/`（需求文档状态表红线）
- UI / 交互类：真浏览器复现 + 复测读数（第 11 条）
- 大批量 LLM 调用（批量复现 / 评测）先报备（Token 控制第 4 条）

## 8. 我要质疑 / 反馈的情形

1. 报的「bug」实为新能力 / 需求变更 → 走需求对接，不是 bug
2. 现象与需求文档「非目标」一致 → 先确认要不要改需求
3. 已登记（待修复 / 修复中）→ 不重复开票（一号一用）
4. 已修复后又出现 → 回归，新票 + 注明回归
5. 给不出特性号 → 先要特性号；确属无票场景（如环境问题）→ 先按排查手册取证，再走需求对接立项

## 9. 完整示例

**负责人**：`Coco，我发现一个 bug：问「第几回」类问题答不出来。`

**我的第一轮回复**（示意，查证结果按实际填写）：

```text
问清：这个属于哪个特性？我按 feat-A004（演义解读）查，若不对请纠正。

两处查证：
1. requirements/feat-A004-sango-classics-rag.md：<查证结果>
   —— 不符合验收标准 / 使目标无法达成 → 是缺陷；命中「非目标」→ 不是缺陷
2. bugs/INDEX.md：bug-00004「问「第几回」类问句无法作答（提问要的回号被注入与 prompt 两端剥离）」
   已登记 · 待修复 → 不新开票

定位：给我 traceId（或我按「命令速查」的「C. 反查」找），我看工具入参 query
      与诊断 query.normalized 是否把回号剥掉了

产出：把本次 traceId 与读数补进 bug-00004；状态维持「待修复」；指派待你定
```
