# 新需求对接流程（负责人 → Coco）

> 用途：把「负责人提需求」到「需求定稿、可以开工」这一段固定下来：谁给什么、我产出什么、一轮对话长什么样。
> 依据：`AGENTS.md` 基本原则 1 / 2 / 5 / 6 / 7、需求文档状态表、`templates/requirement.md`、`requirements/INDEX.md`。
> 一句话：**负责人给「号 + 要什么 + 怎么算做完」，我产出「需求文档 + 登记 + 拆分 + 分支计划」，共同定稿后才开工。**

## 1. 触发

负责人开场（示例）：

```text
Coco，现在我们开始新需求 feat-A013 的开发。下面是我的需求：
1. 需求 XXXX
2. 需求 XXXX
```

要素齐了直接进「我产出什么」；缺「负责人提供什么」里必需的三项之一，我先问再动笔。

### 1.1 听到 `feat-AXXX` 我先查哪里

**需求只有一处存放地：`D:\workplace\dev-docs\requirements\`**（`INDEX.md` 是索引，一份需求一份文档）。听到号，先查再说话：

```powershell
cd D:\workplace\dev-docs\requirements
Select-String -Path INDEX.md -Pattern 'feat-A013'   # 索引里有没有
Get-ChildItem feat-A013-*                           # 文档在不在
```

| 查的结果 | 含义 | 我的动作 |
|----------|------|----------|
| INDEX 与目录都没有 | 新需求 | 按「负责人提供什么」→「我产出什么」对接、起草 |
| 有文档 + 状态 `草稿` | 已在讨论中 | 接着改，不重复起草 |
| 有文档 + 状态 `定稿` / `已提测` | 已开工 | 不重开；改动走 bug 票或另开特性号 |
| 有文档 + 状态 `已归档` | 冻结 | 不得修改；新问题走 `bug-XXXXX`，新能力另开特性号 |

编号必须与 `INDEX.md` 对得上：查不到编号、编号重复或倒退 → 先反馈负责人，不自行改号。

## 2. 负责人提供什么

### 2.1 必需三项

| # | 项 | 说明 |
|---|----|------|
| 1 | **特性号** | 如 `feat-A013`。你指定，我核对 `requirements/INDEX.md`：已存在 / 不符编号规则 → 我提醒你，不自行改号（规则见「命名与编号速查」）。Bug 号不在对接范围：由我按 `bugs/INDEX.md` 自增发行 |
| 2 | **需求条目** | 要做什么 / 解决什么痛点，编号列表最好（我逐条回执，防漏） |
| 3 | **验收口径** | 怎么算做完（可验证：对 / 错，没有灰色地带） |

### 2.2 可选（有则更好，没有我按默认口径推进并标注）

| 项 | 没有时我的默认口径 |
|----|-------------------|
| 优先级 / 期望时间 | 按当前在做的特性排队，不定日期 |
| 涉及项目 | 我按需求推导（前端 mcp-web / 编排 mcp-orchestrator / 后端 mcp-server） |
| 约束（不做什么、技术限制、预算） | 只写「非目标」，约束留空 |
| 现成材料（traceId、日志读数、语料 / 题库、截图、外部接口文档） | 我按手册 `docs/troubleshooting.md` 自查取证 |
| 是否要接口文档先出 | 默认要（第 7 条：小叶依赖老陈） |
| 是否拆故事号 | 默认一个特性一个故事号（大功能才按粒度拆，见「我产出什么」） |

### 2.3 缺项处理

- **只问阻塞项**，一次问清（一轮内问完），不来回挤牙膏
- 不阻塞的按默认口径写进文档，在「风险 & 开放问题」标注，定稿时一并确认
- 负责人未给的验收口径，我先起草候选并标注「待确认」，不替负责人拍板

## 3. 我产出什么（交付物与顺序）

| 步骤 | 产出 | 落点 / 状态 |
|------|------|-------------|
| 1 | **逐条回执**：负责人每条需求 → 映射到文档哪一节（目标 / 非目标 / 验收），漏项当场指出 | 回复正文 |
| 2 | **需求文档**：按 `templates/requirement.md`（背景 / 目标 / 非目标 / 验收 / 接口影响 / 技术要点 / 风险 / 任务与负责人 / 分支计划 / 故事号） | `requirements/feat-AXXX-<slug>.md`，状态 `草稿` |
| 3 | **INDEX 登记**：一行（特性号 / 标题 / 涉及项目 / 状态 / 定稿日期） | `requirements/INDEX.md` |
| 4 | **故事号**：默认 1 个（`story-AXXX-01`）；大功能按粒度拆（需求 / 接口 / 实现 / 前端），登记在文档「故事号」表 | 需求文档内 |
| 5 | **任务拆分 + 负责人 + 依赖**：接口文档先出（老陈）→ 前端（小叶）/ 编排（小胡）/ 后端（老陈） | 需求文档「任务与负责人」 |
| 6 | **分支计划**：dev-docs / 各代码仓的分支名（`{owner}/feat-AXXX_<描述>`） | 需求文档「分支计划」 |
| 7 | **定稿动作**：状态改 `定稿` + INDEX 同步 + 定稿日期 | 定稿后 |

产出顺序固定：**先回执、再文档、后登记**；文档写完才在 INDEX 落行（避免登记了却没内容）。

**讨论即落文档**：讨论中提到的每条需求、约束、验收结论都写进文档（不靠记忆、不攒到最后）；过程性内容（讨论过程、拍板记录、待定项清单）不进文档（第 5 条）。

## 4. 一轮对接长什么样

我的回复固定四段（有则写，无则一句话说明）：

1. **确认**：一句话复述（号 + 标题），确认我没理解偏
2. **需要你补**：阻塞项提问（≤3 条）；没有就写「无需补充」
3. **草稿**：需求文档路径 + 一句话说明范围
4. **待你拍板**：≤3 条，每条附我的建议方案（第 2 条：有异议要给替代方案，不只抛问题）

负责人的回复，三种任选：

| 回复 | 含义 | 我的动作 |
|------|------|----------|
| `定稿` | 认可 | 状态改 `定稿`、INDEX 同步、准备开工（接口文档先出） |
| `改 X` | 改某处 | 改文档 → 复述改动点 |
| `补 Y` | 补信息 | 更新文档 → 若影响范围 / 验收，重新走一轮 |

## 5. 定稿与开工

**状态生命周期以本节为单一维护点**（2026-09-22 决策：从 `AGENTS.md` 迁到此处，那边只留指针与红线，避免多边维护）。每个需求文档头部的 `> 状态：` 字段按此流转，由 Coco 即时更新、不等提醒：

| 状态 | 含义 | 进入时机 |
|------|------|----------|
| 草稿 | 初稿，团队讨论中，不可开工 | Coco 起草需求 |
| 定稿 | 讨论 / 审核通过，可开工 | Coco 与负责人共同定稿 |
| 已提测 | 开发完成、Coco 审查通过，负责人在分支上验收 | Coco 提测（`AGENTS.md` 分支与合并第 7 条） |
| 已归档 | 终态：验收通过并合并上线，**文档冻结不可变更** | 负责人合并 PR 后 Coco 收尾（第 10 条） |

```text
草稿（讨论中，不可开工）── 定稿 ──> 开工（接口文档先出 → 实现 → 审查 → 提测）──> 已提测 ──> 已归档（冻结）
```

- **草稿期不动代码**（第 1 条：无票不动代码）
- 定稿才开工；开工第一步是接口文档（第 7 条），前端不等接口文档不开工
- **`已归档` = 终态、冻结**：归档后不得再修改该需求文档（含回填 bug、补记验收结论、补充说明）；后续问题走 bug 票，新能力另开特性号
- 归档登记（状态置「已归档」+ 验收 / 目标勾选 + `requirements/INDEX.md` 同步）是该文档最后一次改动，由 Coco 在 PR 合并后一次性完成
- 旧写法 `已定稿` 与 `定稿` 同义，文档被改动时统一为 `定稿`
- 对接尽量开新会话完成（Token 控制第 6 条：阶段分隔），别和排查历史混在一起

## 6. 边界与红线

| 红线 | 来源 |
|------|------|
| 草稿期不开工、不动代码 | 第 1 条 + 状态表 |
| 需求文档只记需求：背景 / 目标 / 非目标 / 验收 / 接口影响 / 技术要点 / 风险 / 任务 / 分支 / 故事号；讨论过程、拍板记录、待定项清单不进文档 | 第 5 条 |
| 一份需求一份文档，我与负责人共同定稿，全员阅读 | 第 6 条 |
| 接口文档先出，小叶依赖老陈 | 第 7 条 |
| 文档轻：小团队、小文档；老陈的技术方案并入接口文档 | 第 5 条 |
| 大批量 LLM 调用（批量评测 / 批量数据生成）先报备 | Token 控制第 4 条 |

## 7. 定稿前自检清单（我逐条过）

- [ ] 负责人每条需求都有落点（目标 / 非目标 / 验收），无漏项
- [ ] 每条验收标准可验证（对 / 错，无灰色地带）
- [ ] 非目标写清了「本次不做的事」
- [ ] 接口影响点了（API / MCP 工具 / 前端路由）
- [ ] 依赖与顺序定了（接口文档先出、有无前置 bug 票）
- [ ] 分支计划与故事号已登记
- [ ] 与已归档需求无重叠（重叠就并入或另立，不重复做）
- [ ] 范围可在一个特性内交付（过大则建议拆分并给方案）
- [ ] 文档里没有过程性内容（讨论、拍板、待定项）

## 8. 我要质疑 / 反馈的情形（第 2 条）

出现下列情况，我不盲从，先说清理由与替代方案，由负责人定：

1. 需求与现有架构 / 契约冲突（如要求改已冻结的归档文档）
2. 与已归档需求重复，或应并入在做的特性
3. 验收口径不可验证（「答得更好」这类）
4. 单特性范围过大（三侧大改 + 新表 + 新契约），建议拆成两个特性
5. 需求依赖大批量 LLM 调用（须先报备，第 4 条）
6. 流程本身繁琐 / 不合理（第 10 条：随时可提，确认后同步 `AGENTS.md`）

## 9. 命名与编号速查

| 项 | 规则 | 例 |
|----|------|-----|
| 特性号 | `feat-{年份字母}{三位数字}`，每年重置，A=2026 | `feat-A013` |
| 需求文档 | `requirements/feat-AXXX-<英文短横线描述>.md`（唯一存放地 `D:\workplace\dev-docs\requirements\`） | `requirements/feat-A013-recall-rerank.md` |
| 故事号 | `story-{特性号}-{两位序号}`；默认 1 个，大功能按粒度拆 | `story-A013-01` |
| 分支 | `{owner}/feat-AAA_<简短描述>`；owner：`coco` / `ye` / `hu` / `chen` | `coco/feat-A013_recall-rerank` |
| 提交 | `#story-A013-01 feat: <中文描述>` | — |

## 10. 完整示例

**负责人**：

```text
Coco，现在我们开始新需求 feat-A013 的开发。下面是我的需求：
1. 召回结果加一层重排，现在的 top1 经常不是最好的
2. 日志页能看到重排前后对比
```

**我的第一轮回复**（示意）：

```text
确认：feat-A013 召回重排（top-N 重排 + 日志页前后对比）

需要你补：
1. 重排的验收口径：用什么算「重排后更好」？（我建议：给定 5 条你标的问句，重排后目标回目进入 top3）
2. 重排放 sango 侧还是总台侧？（我建议 sango 侧：召回与重排同处，总台零改契约）

草稿：requirements/feat-A013-recall-rerank.md（草稿）

待你拍板：
1. 是否顺带把「重排前 top-N 快照」落进诊断（不落则日志页对比做不了）—— 建议落，属 A009 诊断扩展
2. 涉及三侧改动（sango 重排 + 总台透传 + 前端面板），建议按 需求 / 接口 / 实现 / 前端 拆 4 个故事号 —— 建议拆
```

**负责人**：`定稿`（或 `改 1` / `补 2`）→ 我改状态、同步 INDEX、准备开工（接口文档先出）。
