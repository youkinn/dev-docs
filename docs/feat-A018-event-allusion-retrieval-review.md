# FEAT-A018 事件 / 典故检索装配 —— 可读性与可扩展性评审 + 改造建议

> 用途：对事件桥 / 典故桥的检索侧装配代码做结构评审，沉淀问题清单与改造建议，供负责人拍板是否立项；本文件是评审与建议稿，不是契约，不产生行为变更。
> 评审对象：`mcp-server/sango/src/search/sango-index.ts`（search 装配层）与 `mcp-server/sango/src/search/event-table.ts`（双表模块）。
> 状态：已落地（2026-10-09 负责人验收通过，随 story-A018-01 提交）。日期：2026-10-09。

## 0. 结论

- 骨架是好的：事件 / 典故双表同构，共用 `createTableModule` 工厂（加载 → V 校验 → 漂移检测 → 单例重建 → 桥匹配），两路各自独立降级、互不影响，是全代码扩展性最好的部分。
- 主要问题集中在 `SangoIndex.search()` 装配层：约 300 行的上帝方法承载全部规则，事件 / 典故并池、L3 锚点、置顶、重排的差异靠散落的 type 分支与复制粘贴表达。
- 按性价比排序的改造建议见 §3；全部为纯代码收敛 / 行为零变化的重构，落地需开票（建议挂 feat-A018 后续号或新特性号，由负责人定）。

## 1. 现状结构（最小）

- `event-table.ts:145` `createTableModule(config)`：双表共用工厂，事件路（type=L1/L2/L3）与典故路（type=典故，无 L3）各自一个实例（`event-table.ts:350` / `:360`）。
- `sango-index.ts:631` `search()`：三路召回（BM25 / 向量 / 标签）→ 桥命中 → 事件 L1/L2 并池 → 典故并池 → 增强查询重排 → L3 锚点置顶 → 保证区排序 → cross-encoder 重排 → 取窗 → 诊断装配，全部在同一函数内串行完成。

## 2. 问题清单

### 2.1 可读性问题

- **search() 上帝方法**（`sango-index.ts:631`）：三路合并、两类并池、锚点、排序、诊断全在一个函数，局部变量十几个，单点改动需通读全函数判断影响。
- **注释编号与执行顺序脱钩**："③ L1/L2 并池"（`:784`）、"④ 池内重排"（`:806`）先执行，"② L3 锚点置顶"（`:827`）在最后。编号是契约文档章节号，不是执行顺序；按 ①②③④ 读会得出错误流程，且 L3「不进重排、分数为未增强初始分」的行为差异就藏在这种错位里，改序时极易破坏。
- **同一打分公式手写多处**：三路合并内联（`:751`-`:756`）、纯向量兜底特例（`:758`-`:771`）、`unifiedScore`（`:986`）、`rescorePoolWithEnhancedQuery`（`:1055`-`:1065`）。`unifiedScore` 存在但三路合并不调用；权重历史上已多次定参，改一处漏一处即口径漂移。
- **chunkId → 文档下标反查重复**：`docIndexOf.get(chunkId) + undefined 过滤` 至少出现 5 处——事件并池、典故并池、L3 锚点（`:1003`）、`buildEventHit`（`:1156`）、`eventDocSetOf` / `allusionDocSetOf`（`:1199` / `:1261`）。
- **排序比较器内嵌业务策略**：`pinDocs.size > 1` + `segPick`（`:870`-`:883`）把「死亡意图段序策略」塞进 sort 回调；死亡、登场、L3 三类来源挤进同一个 pinDocs，段序语义却只由 `deathIntent` 派生，登场靠默认值顺带得到行为，隐式且难维护。
- **L1/L2/L3 无语义注释**：类型定义（`event-table.ts:24`）与装配处只解释 L3 是「标签位点段 ±N 小位点组」（`sango-index.ts:828`），L1/L2 是什么、三者差异需翻接口文档。

### 2.2 可扩展性问题

- **装配侧靠复制粘贴扩展**：事件并池循环（`:786`-`:793`）与典故并池循环（`:795`-`:802`）结构完全相同，L3 再一份（`:828`-`:838`）。新增一条桥路需新写：并池循环、poolDrivers 项、命中明细 builder、docSet builder、诊断上下文与空值分支，至少 5 处。
- **桥优先级隐式**：`poolDrivers` 数组顺序（事件在前、典故在后，`:808`-`:813`）即增强查询的取组优先级，新增一路须记得插在正确位置，规则未声明为数据。
- **L3 特判分散**：search 双重 filter（`:778`-`:779`）、锚点循环（`:828`-`:838`）、`buildEventHit`（`:1171`）、`eventDocSetOf`（`:1206`）、排序保证区（`:870`）共 5 处；将来出现「典故 L3」或新层级，每个点都要同步改。
- **保证区无扩展点**：pinDocs 是死亡 + 登场 + L3 锚点的隐式并集，段序策略与意图耦合在 sort 比较器，新意图（如带段序语义的登场）没有现成挂载点。

## 3. 改造建议（按性价比排序，均为行为零变化重构）

### 3.1 统一打分入口（低成本，收益最大）

- 把三路合并与纯向量兜底改为调用 `unifiedScore`，消除公式复制。
- 理由：打分公式是全检索的核心恒等式（诊断复算依赖，bug-00013），单一入口后权重调整只改一处。
- 代价：兜底路径的加权公式是「无词法命中」特例，需在 unifiedScore 或调用处显式表达，保持逐字节一致。

### 3.2 收敛「组并池」与「组 → docSet」助手

- 抽 `poolGroupChunks(groups)` / `groupDocsOf(groups)` 一类助手，收掉 5 处重复反查与 3 份并池循环。
- 理由：新增桥路从「复制」变「传参」，L3 差异收敛为显式参数（是否参与重排 / 是否进保证区）。
- 代价：需小心保持 inPool 去重、加入顺序（影响重排前规则序）与现实现一致。

### 3.3 桥段注释改按执行顺序

- ①②③④⑤ 编号改按执行顺序，或改为描述性阶段名（如「并池」「增强重排」「锚点置顶」），消除「② 晚于 ④ 执行」的读码陷阱。
- 代价：注释变更不影响行为；契约文档章节号保留在 JSDoc 里供追溯。

### 3.4 显式化语义与优先级

- 在 `event-table.ts:24` 类型定义处补 L1/L2/L3 语义一句话，或指向接口文档章节。
- `poolDrivers` 改为显式优先级（如 `{ priority }` 字段 + 排序），或加注释声明「事件 L1/L2 恒在典故之前」的规则来源。

### 3.5 保证区策略对象化（预留扩展口）

- 把 `segPick` 段序策略从 sort 比较器剥离为「保证区策略」小对象（命中来源 → 是否参与 / 段序语义），为后续意图（如登场段序）留挂载点。
- 代价：改动面最大的一条，建议前四条落地稳定后再做。

## 4. 验证方式

- 行为零变化断言：改造前后同 query 出参逐字节一致（entries 顺序、finalScore、诊断 candidates 与 eventHit / allusionHit）。
- 复用现有回归：`dev-docs/test/sango-tag-route-audit.mjs` 复刻口径、sango-recall-bench 回归基线；落码后跑一遍对照。
- 对照样例：事件（L1/L2 并池命中）、事件（L3 锚点置顶）、典故命中、双路均未命中、表降级路径各至少一例。
