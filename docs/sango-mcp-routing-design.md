# 问答系统 MCP 路由完整方案

---

## 一、方案总览

### 核心设计思想
**「确定性优先 + LLM 自主决策兜底」**——能用前端交互和本地规则搞定的，坚决不消耗 LLM 推理资源；LLM 自主决策仍保留，只是优先级放到最后：当前三层都无法明确判定时，才让大模型做兜底判断（2026-09-16 负责人确认：不是推翻 A003 单 Agent 自主决策，是确定性优先、LLM 兜底，最低限度减少 LLM 调用产生的 token 与耗时）。

### 整体四层路由架构
```
用户请求
    ↓
第一层：前端标签判定（显式意图，0ms）→ 命中直接路由
    ↓ 未命中
第二层：本地关键词硬匹配（规则拦截，<1ms）→ 命中直接路由
    ↓ 未命中
第三层：向量相似度匹配（风云三国高置信识别，<100ms）→ 命中直接路由
    ↓ 未命中
第四层：轻量大模型兜底（四分类语义推理，~500ms）→ 最终路由
    ↓
调用对应工具（天气 / 三国演义走 MCP，风云三国走本地 sango_query）→ 人名别名归一化 → LLM 生成答案 → 返回用户
```

### 各层覆盖率预估
| 层级 | 覆盖率 | LLM 调用 | 耗时 |
|-----|-------|---------|------|
| L1 前端标签 | 60%~80% | 无 | 0ms |
| L2 关键词匹配 | 10%~20% | 无 | <1ms |
| L3 向量匹配 | 5%~10% | 无 | <100ms |
| L4 大模型兜底 | <5% | 有 | ~500ms |
| **最终答案生成** | 100% | 有 | 2~3s |

**整体收益**：95% 以上的请求路由环节零 LLM 消耗，总响应时间稳定在 3 秒以内，路由相关 Token 成本降低 90% 以上。

## 二、路由分层设计（方案，2026-09-16 定稿：L1 已落地，L2/L3/L4 待实现）

### 第一层：前端标签判定（优先级最高）【已落地：/api/chat 的 domain】
**触发条件**：用户点击顶部标签页（天气 / 风云三国 / 三国演义）

- 后端直接读取前端传参的标签标识，跳过所有后续路由判断，直接绑定对应 MCP 和专属系统提示词
- 设计依据：用户主动点选标签 = 明确告知使用场景，是最高优先级的意图信号，零延迟零误判

### 第二层：本地关键词硬匹配【待实现】
**触发条件**：用户未选择标签，进入后端自动路由

维护三个工具的专属关键词字典，命中任意关键词直接路由：

| 工具 | 专属关键词列表 |
|-----|--------------|
| 天气 MCP | 天气、气温、下雨、下雪、湿度、风力、晴天、阴天、温度、降雨、雷暴、大风、出门、游玩、旅游 + **美国** |
| 三国演义 MCP | 字、籍贯、官职、生卒年、原著、章节、第几回、原文、生平、演义、三国时期、罗贯中 |
| 本地 sango_query 工具 | 风云三国、MOD、骑砍、招募、答题、好感度 |

### 第三层：向量相似度匹配（风云三国高置信正向识别）【待实现】
**核心定位**：只做风云三国招募题的高置信正向识别，不做任何反向推定

1.  **预处理阶段**：将当前 88 道风云三国招募题全部向量化，存入内存
2.  **实时处理阶段**：用户提问生成向量后，与全量题库计算余弦相似度
3.  **阈值判定规则**：
    - 相似度 ≥ 0.9 → 高置信命中游戏招募场景，直接走本地 sango_query 工具
    - 相似度 < 0.9 → 不做任何猜测，直接进入第四层大模型统一判断
4.  **重叠题校正逻辑**："字、籍贯"这类重叠度极高的关键词，标记为模糊关键词，命中后不直接路由到三国演义，先进入向量层做二次判定，避免把游戏招募题误分到文史场景

### 第四层：轻量大模型兜底【待实现】
**触发条件**：前三层均无法明确判定

调用极简提示词做四分类判断，仅输出数字编号，不生成任何答案内容：

```
你是路由助手，请判断用户问题属于哪个类别，只返回数字编号：
1: 天气查询
2: 风云三国游戏问答
3: 三国演义原著问答
4: 以上都不是 / 无关问题

用户问题：{{用户问题}}
输出：
```

**返回结果处理**：
- 返回 1 → 天气 MCP
- 返回 2 → 本地 sango_query 工具
- 返回 3 → 三国演义 MCP
- 返回 4 → 无关问题，直接返回引导话术，不调用任何工具

## 三、工具调用与答案生成

路由确定目标工具后，进入答案生成流程：

### 1. 调用对应工具
- 天气 MCP → 查询实时天气数据
- 本地 sango_query 工具 → 检索游戏招募题库答案 + 游戏属性数据
- 三国演义 MCP → 检索 120 章 JSON 知识库相关章节内容

### 2. 人名别名归一化（已实现：alias.json）
在三国演义检索前，先做本地人名映射，全程不消耗 LLM 资源：
- 已实现：`mcp-server/sango/data/alias.json`（别名 → 人物 ID，P001 起按规范名去重，关羽 → P002）
- 关羽 / 云长 / 关云长 / 美髯公 → P002；诸葛亮 / 孔明 / 诸葛孔明 / 卧龙 → P005
- 实现方式：本地哈希字典 O(1) 匹配

### 3. LLM 生成最终答案
将工具返回的原始数据 + 对应场景的系统提示词 + 用户原始问题，一起发给大模型生成白话文答案。

**各场景系统提示词核心约束**（对齐 orchestrator 现有 UNIFIED_SYSTEM_PROMPT：能力一 5 条 / 能力二 5 条 / 能力三 6 条 / 无关域自由作答）：

| 场景 | 系统提示词核心约束 |
|-----|------------------|
| 天气问答（能力一 5 条） | 1. 只输出一句话纯文本，总字数不超过 50 字（含标点），不要换行、不要 Markdown 标题/表格/分点列表或多段建议；2. 结论优先：适合 / 基本适合但需准备 / 建议调整时间 / 不建议出行，紧跟日期和地点；3. 只写影响结论的天气依据：温度用摄氏度（℃）换算后取整，再写降水或预警，不罗列风力等次要数据；4. 以「出门必备：」结尾，列出手机、乘车码或交通卡、证件、钥匙，天气需要时再追加雨伞、薄外套等；5. 不输出未来几天预报、预警区域细节或用户没问的建议 |
| 风云三国问答（能力二 5 条） | 1. 收到用户提问后必须先调用 sango_query 工具（参数 text 传用户原始问题），取回候选题目；2. 先理解用户问题含义，再判断候选中哪条含义相同（问法不同但含义相同即对应）；3. 判定出对应题目后，只输出该题答案原文，不输出题干、选项字母、解释或任何多余文字；4. 候选中没有含义对应的题（含只是字面相似、含义不同），只回复「题库未收录该题，请换个问法」；5. 禁止使用题库之外的知识作答、补充或改写答案 |
| 三国演义问答（能力三 6 条） | 1. 回答前必须先调用 sango_novel_search 工具检索《三国演义》原文（domain=sango-novel 快路径：系统已预先检索并注入片段，模型不再调工具，直接依据片段作答）；2. 只依据工具返回的原文作答：人物、情节、数字都必须能在原文里找到；3. 人名一律以召回原文为准：原文写谁就是谁，不得按常识/记忆替换、不得补别名、不得解释成别人；4. 原文里没有相关内容的问句，必须回答「演义中未涉及」，禁止用先验知识补全；5. 不评价、不纠正、不对比：不得说原文写错，不得提正史/影视/游戏，不得出现「实际上是…」这类转折；6. 回答格式固定：先写一句结论，然后写「引用的原文」（出处：第X回 回目），出处只到回目、不写段落编号，有多段时匹配优先度最高的那一段即可。服务端另做本地引用校验（答案人物 ⊆ 召回人物，本地别名表扫描，0 次 LLM）+ 固定格式校验，不过 → 兜底（原文片段 + 出处 + 结论句） |
| 无关问题 | 不调用任何工具，凭自身知识自由作答，简洁清楚；不套用天气播报格式、不套用题库话术，不确定时直接说明 |

## 四、风云三国题库维护方案（后面再做）

### 增量更新机制
不需要每次题库变化都全量重新向量化，采用增量追加方式：

1.  **新增题目**：出题机生成新题后，只对新题目单独向量化，直接追加到现有向量库末尾，毫秒级完成
2.  **修改题目**：只替换对应题目的向量条目，不影响其他题目
3.  **删除题目**：只移除对应题目的向量条目
4.  **持久化**：定期将全量向量保存到本地文件，服务重启时直接加载，不用重新计算

### 性能边界与升级标准

暴力遍历全量向量做相似度计算的性能天花板：

| 题库规模 | 单次检索耗时（单核 CPU） | 方案适用性 |
|---------|------------------------|-----------|
| 100 题 | <1ms | 完全适用，无压力 |
| 1,000 题 | ~5ms | 完全适用 |
| 10,000 题 | ~50ms | 完全适用，用户无感知 |
| 100,000 题 | ~500ms | 建议升级为 HNSW 近似索引 |

**结论**：当前 88 题起步，就算出题机疯狂生成到 1 万题，暴力遍历方式都完全够用，不需要提前上重型向量数据库。

## 七、方案优势总结

1.  **成本极低**：95% 的请求路由环节零 LLM 消耗，只有答案生成环节调用一次 LLM
2.  **响应极快**：路由环节总耗时 <100ms，加上答案生成，整体稳定在 3 秒以内
3.  **准确率高**：前三层确定性逻辑准确率 100%，只有不到 5% 的请求交给大模型判断
4.  **维护简单**：关键词和题库都可以配置化更新，不需要改核心代码
5.  **扩展性强**：二期三国志功能完全预留，零侵入即可快速上线
