## 1. 适用与不变量

适用范围：`source=sanguo-yanyi`（毛本 120 回）。二期《三国志》沿用同一套算法，只换语料。

切分必须满足以下不变量，任一不满足即视为构建失败（与编译失败同级）：

| # | 不变量 | 校验方式 |
|---|---|---|
| I1 | 同回 chunk 文本拼接 **逐字节等于** 原文段拼接（不增、不删、不改、不重） | §7；当前 PASS |
| I2 | 单个 chunk **不跨回** | 计数须为 0；当前 0 |
| I3 | **切点必须落在句末标点（`。！？；`）之后**；唯一例外是源段边界处源文本本身无句末标点（以段边界为切点） | 计数须为 0；当前 **0 违规**（源段边界例外 0 处） |
| I4 | 答案句不被切碎（判定正则仍能命中至少一个 chunk） | 24 例基准须 0 例失败；当前 0 |
| I5 | 每个 chunk 携带完整元数据：`chunk_id / parent_id / seq_in_parent / type / role / text / char_count`（可选 `group_id`）；出参逐条展开回级 `chapter / title` | schema 校验（§5） |
| I6 | `chunk.text` **为纯原文**，不含出处、回目、段号、类型、分数等元数据；注入视图的 id 标签由服务端拼接，不进语料文本 | schema 校验（§5） |
| I7 | 无 chunk 超 400 字硬上限 | 计数须为 0；当前 0 |
| I8 | 长度 < 80 字的 chunk（碎片回并残余） | 非 verse 残余 ≤ 12；verse 完整诗篇单列、不设上限（口径见 §4.4）。当前：非 verse 残余 1、verse 完整诗篇 163 |
| I9 | **引语（`“ ”`）不被切断**：单个引语整体落在同一 chunk 内；仅当引语自身超 400 字硬上限时退回按句切 | 构建期自检：块内 `“` 多于 `”` 时回溯配对 `”` 计其跨度，跨度 ≤ 400 字即违规；当前 0 违规（6 处豁免均 > 400 字；源文本引语未闭合 1 处，同样豁免） |

> I6 的目的不是「让出处消失」，而是**把出处与引用原文的渲染权收归服务端**：语料文本保持纯净，服务端才能用字段稳定渲染；同时注入文本不含出处，模型无从抄写，也就不会把出处写进输出（省输出 token）。详见 §6。

## 3. 切分算法（六步，规范正文）

```
输入：某回 segments[{index,type,text}]，参数 TARGET=250 / CAP=400 / MIN=150

步骤 1  切句：按句末标点 。！？； 切分，得到句子序列（不切句内）
步骤 2  装箱：顺序装箱到 TARGET，至少装 1 句；受 CAP=400 硬上限约束
步骤 3  分组：同回内连续 narration 段合成一个流，跨段装箱；verse / comment 段内独立装箱
步骤 4  收尾（碎片回并）：**非 verse** 块长度 < MIN=150 时并入同回前块，跨类型允许；并入后越 CAP=400 则不并；verse 块（完整诗篇）不并入、保持独立
```

设计取舍说明：

- **为什么不做通用递归切分。** 中文「默认分隔符失效」的坑（分隔符不在文本里、切完还是超长）在本库不成立：句末标点 `。！？；` 是硬边界，实测句长 p99=51 字、max=180 字，全部小于 TARGET=250。**因此「装箱」永远不会遇到「单句超长必须再切」的情况**，递归的第二层退化为空。少一层机制，少一类 bug。
- **装箱越过 TARGET 受 CAP=400 约束**：实测越界量 p90=358 字、max=400 字（§7 I7=0）。
- **步骤 3 的跨段**只在 `narration` 之间发生；诗词与评注段内独立（诗篇判定口径见 §4.6）。

## 4. 参数决策（每项含实测）

全部数字来自 `node --experimental-strip-types mcp-orchestrator/scripts/probe/chunk-sweep.mjs`（段级语料默认不落盘，复跑前用 `SANGO_EMIT_SEGMENTS=1` 临时生成 `data/corpus/_segments/`）。列名口径：`@k` 答案段折算命中；`750/1000 覆盖` = 按排名累加 chunk 字数到预算上限时答案是否已进入注入；`top5重复` = top5 内存在共享整句的 chunk 对。

### 4.2 重叠：0

| 重叠 | 均长 | @1 | @3 | 750 覆盖 | 1000 覆盖 | top5 重复 |
|---|---|---|---|---|---|---|
| **0（推荐）** | 236 | 17/24 | 21/24 | **21/24** | **22/24** | **3/24** |
| 1 句（≈18 字） | 252 | 18/24 | 21/24 | 20/24 | 21/24 | 16/24 |
| 2 句（≈36 字） | 269 | 18/24 | 20/24 | 19/24 | 20/24 | 19/24 |

**不留重叠。** 重叠在检索侧零收益（750 覆盖 21→20→19 单调变差），却让 top5 里出现大量近重复块（3→16→19，即 67% 的查询 top5 含重复内容）。这与本迭代的目标直接冲突：注入预算只有 750~1000 字，重复块白吃预算。

> 关于「overlap 10% 惯例」：那是**长文档 + 无结构化边界**场景的经验值（切在句中会丢语义，只能靠重叠补偿）。本库两条前提都不成立——切点在句末标点（语义完整），且答案句可被 250 字窗口整体包住。**所以本库重叠的收益为 0、代价为正，结论是不留。**

### 4.3 跨段：允许（同回内连续叙述段）

下表为**终配参数**（250 目标 / 400 硬上限 / 软下限 100 / 跨段）下的对照：

| 配置 | chunk 数 | 均长 | 最短 | <80 字 | @1 | @3 | 750 覆盖 | 1000 覆盖 | top5 重复 |
|---|---|---|---|---|---|---|---|---|---|
| 不跨段（段内切分） | 2443 | 242 | 6 | 38 | 19/24 | 20/24 | 20/24 | 20/24 | 6/24 |
| **跨段（推荐）** | 2263 | 262 | **33** | **10** | 19/24 | 20/24 | 20/24 | 20/24 | **5/24** |

**结论：跨段的真实收益是「消碎片」，不是「提排名」。** 两档 `@1/@3/覆盖` 完全持平，跨段把不足 80 字的碎片从 38 个压到 10 个、最短块从 6 字抬到 33 字，top5 重复 6→5。

> **补正（原稿此处的表述有误）**：原稿写「跨段 top5 重复更低（3 vs 5）」并据此选跨段，那是另一组参数下的读数；统一参数下两档变为 6 vs 5，且 `@1` 同为 19/24。**选跨段的理由应改记为「碎片清理」**：38→10 个 <80 字块、最短 6→33 字——这些块几乎不可能被召回，纯属索引噪声。段边界是网页折行产物，不是叙事边界，跨段更贴近语义单元。

### 4.4 尾部碎片软下限：150 字（碎片回并）

碎片回并口径：**非 verse 块长度 < 150 字时并入同回前块**，跨类型允许（短叙述段可并入前一块），并入后越 400 字硬上限则不并；`verse` 块是完整诗篇（均 40~60 字，如「后人有诗赞二人曰：……」），**语义自足的最小检索单元，不并入前块**。并入前块的理由是召回成本：两块才拼出关键证据时，检索必须同时命中才有效。

当前读数（底本 = 人民文学出版社版）：长度 < 80 字的 chunk 共 164 个，其中 **verse 完整诗篇 163 个 / 非 verse 残余 1 个**——非 verse 残余已从回并前的 6 个压到 1 个（该例前块已卡 400 字上限，并入即越 I7）。

> **「以源段为最小单位、不拆源段」不可行（实测否证）**：源段均长 294 字，**1079 段超 250 字、538 段超 400 字**，段内必须按句装箱；强行不拆段反而把 < 150 字的块从 187 个抬到 363 个、均长抬到 268 字。**「按段关联」只能用于合并侧**（碎片回并、引语整体不切、引诗句与其后诗体同段），不能替代按尺寸装箱。

> **残余成因**：非 verse 残余一律卡在「前块已达 400 字上限」或「该回首块」两个条件下；补「并入后块」分支无效（实测一个都消不掉），清零只能放宽 CAP，而 §4.1 显示尺寸变大即回退，得不偿失。接受该残余。

### 4.5 硬上限：400 字

目标尺寸之上设硬上限 400 字（I7），用于兜底跨段装箱的越界，保证注入片段长度不超过预算预期。

**为什么是 400 而不是 500。** 两档的检索指标完全相同（`@1/@3/覆盖` 均为 19/20/20），但：

| 上限 | 超 400 字块 | 超 500 字块 |
|---|---|---|
| **400** | **0** | **0** |
| 500 | 154（7%） | 0 |
| 600 | 158（7%） | 92（4%） |

400 是 I7 硬上限的取值本身：选 400，max=400 与 I7=0 天然自洽；选 500 则**允许 154 个块（7%）突破 400**，注入片段长度不可预期，与「注入收窄到 750~1000 字预算」的目标直接冲突，**故取 400，500 不采用**。

### 4.6 诗词 / 评注（verse 独立打包）

`verse` 198 段（诗篇）、`comment` 2 段：**段内独立打包，不与叙述段混装**。

隔离 vs 不隔离实测（终配参数）：

| 配置 | chunk 数 | @1 | @3 | 750 覆盖 | 类型分布 |
|---|---|---|---|---|---|
| 隔离 type（终配） | 2263 | 19/24 | 20/24 | 20/24 | verse 422 / narration 1837 / comment 4 |
| 不隔离 type | 2226 | 18/24 | 20/24 | 20/24 | verse 258 / narration 1968 |

**隔离无害且 `@1` 略优（19 vs 18），维持隔离。**

> **诗篇判定口径（C3 落地后）**：`classify()` 的行级判定 + `refine_verse()` 的诗句级切分——含诗词标记的融合段在「首个诗词标记所在句的起点」切开，前半归 narration、后半归 verse，`type` 因此可作为「这段是诗」的语义保证使用。
> **引语内的标记不计**：标记（`诗曰/歌曰/有诗/诗一首`…）出现在引语 `“ ”` 内部时不再判为 verse——引语里转述的谣谚（如第 35 回「闻新野之人歌曰：'新野牧，刘皇叔……'」）是叙述内容，不是诗篇；第 79 回、第 114 回同类误判一并消除。
> 当前读数：段级 verse 198 / narration 1810 / comment 2；chunk 级 verse 201 / narration 2444 / comment 4。

## 5. 语料 schema v2（文本与元数据分离）

这是 §6 的前提，也是本次唯一的**契约变更**。

```jsonc
{
  "source": "sanguo-yanyi",
  "chapter": 73,
  "title": "玄德进位汉中王　云长攻拔襄阳郡",
  "chunks": [
    {
      "chunk_id": "sanguo-yanyi:0073:p0005:c01",  // 见下方「ID 规则」
      "parent_id": "sanguo-yanyi:0073:p0005",
      "seq_in_parent": 1,
      "type": "prose",
      "role": "body",
      "text": "瑾曰：“特来求结两家之好……请君侯思之。”云长勃然大怒曰：“吾虎女安肯嫁犬子乎！……”",  // 纯原文
      "char_count": 45,
      "group_id": "sanguo-yanyi:1b4197a4"         // 上下文组；孤立段不带该键
    }
  ]
}
```

**ID 规则**：`parent_id` = `{source}:{回号4位补零}:p{段号4位补零}`；`chunk_id` = `{parent_id}:c{seq_in_parent 两位补零}`。
- 段 = 原文一行（回目行不入段），段号 = 该回正文行序号；块 ⊂ 父段，块不跨段。
- `chunk_id` 可由 `parent_id + seq_in_parent` 回放；回内位置 = （段号，块序），引用排序按该二元组。

**取值**：`type ∈ prose|verse`（正文 / 诗词），`role ∈ body|lead`（主体 / 引题）。
- 枚举值、类型与启动校验唯一维护在 `mcp-server/sango/src/chunk-kind.ts`；语料出现表外取值时加载期抛错终止启动。
- `role=lead` 的引题块照常加载 / 出块，**不进检索索引**（BM25 / 向量 / 标签均不收录）。
- 展示层需要中文文案时在展示模块局部映射，不反向影响语料取值。

**工具出参的回级字段展开（2026-09-18 补，Coco）**：`chapter` / `title` 在**语料文件里是文档级**（按回分文件，不重复），但 `sango_novel_search` 的**出参条目必须逐条携带** `chapter` / `title`——检索跨全库，单次召回的多条条目可来自**不同回**（top5 跨回是常态），编排侧只能逐条渲染出处；且 orchestrator 进程不读 mcp-server 的语料目录，无法「按 id 回溯回文件」。注入时这两个字段被剥离，不进模型上下文（§6.3 第 5 点）。

变更点与理由：

| 变更 | 现状 | v2 | 理由 |
|---|---|---|---|
| 检索单元 | `segments[]`（整段） | `chunks[]`（250 字目标） | §4.1 |
| 元数据位置 | 检索侧拼接进文本（`【出处】第N回 … · 段M（类型）`） | **独立字段**，文本内一律不含 | I6；§6 |
| 位置键 | 无（单元即段） | `parent_id` + `seq_in_parent` | 出处展示、父子映射、引用排序、人工回溯原文 |
| 单元 ID | 无 | `chunk_id`（段号 + 块序） | 评测脚本与日志可稳定引用（避免用「第几块」这种易漂移的定位） |
| 类型 / 角色 | 无 | `type` / `role`（英文枚举） | 代码分支可穷尽校验，不受展示文案改动影响 |
| 引用原文 | 模型抄写 | **由服务端按 `[片段N]` 字标从条目 `text` 回填整段** | §6：引用原文由服务端渲染，模型不生成 |

> `segments[]` 保留在构建期中间产物中（清洗与类型标注的产物），最终交付目录只放 `chunks[]`。

## 6. 「出处与引用原文由服务端渲染」的落地设计

### 6.0 需求原意（负责人 2026-09-18 澄清，原稿表述有误）

**需求要的仍然是「出处标题 + 引用原文」照常展示**，变的只是**由谁产出**：这些内容**不经由大模型吐出**，因为有些原文很长，会让模型多消耗**输出 token**。

原稿把这条写成「模型不回答出处」「让出处变成服务端可控项」，并据此推导出「注入里不出现出处 → 模型没有出处可抄」——**方向对，但目标写偏了**：真实目标不是「消灭出处」，而是**「省输出 token + 保证原文逐字可信」**。因此正确表述是：

> **凡是由元数据或原文决定的内容，一律服务端渲染，模型只输出结论 + 一个短指针。**

由此，语料库要做的事是：**把「出处」冗余成字段**（`chapter / title / chunk_id / parent_id / seq_in_parent`，引用原文即条目 `text` 本身），让服务端有能力在不问模型的情况下，按 `[片段N]` 字标把「引用原文 + 出处」拼出来。

### 6.2 代价量化（24 例基准，引用原文）

口径：量「模型若仍须自行输出引用原文 + 出处」须吐的字数；新方案只吐字标。

| 项 | 均 | p50 | p90 | max |
|---|---|---|---|---|
| 引用原文长度 | 56 字 | 27 | 114 | **234** |
| 出处后缀 `（出处：第N回 回目）` | 25 字 | 25 | 26 | 27 |
| **现状单条引用须吐** | **83 字** | **54** | **143** | **263** |
| 新方案（只吐字标，如 `[片段1]`） | 5 字 | 5 | 5 | 5 |

- 引用原文长度分布（18 例）：`≤10 字 2｜21-40 字 9｜41-80 字 2｜>80 字 5`——**长尾明显**，最长 234 字（第 85 回）。
- **单条引用省 78 字（94%）**，最长一条省 258 字。若一次回答引 2~3 条，省 160~230 字。

> 换算成 token 需按实际 tokenizer 复核（不同分词器对中文的切分差异较大）。**验收时须用线上 tokenizer 量一遍单条引用的输出 token 降幅**，不要直接用字数替代。

### 6.3 语料侧怎么支撑

1. **文本纯净（I6）**：`chunk.text` 只含原文；出处、回目、段号、类型、分数一律走字段。
2. **引用原文 = 条目 `text` 本身**：`citations` 按 `[片段N]` 字标回填整段原文，无任何构建期抽取。
3. **元数据冗余**：`chapter / title / chunk_id / parent_id / seq_in_parent` 独立字段，服务端据此渲染 `（出处：第73回 玄德进位汉中王　云长攻拔襄阳郡）`。
4. **工具出参结构化**：`sango_novel_search` 不再把出处拼进文本块，改为返回结构化条目（字段见 §5）。**接口变更，接口文档先行**（`mcp-orchestrator/api/feat-A004-sango-classics-rag.md` 的「出参」与验收标准 ② 需同步修订）。
5. **注入视图只给纯原文 + 字标**：片段只带服务端编号（如 `[片段1]`），**不带回目、不带段号、不带分数**。**不回目 → 模型无从抄写出处**，回目污染断言扫描的坑（`agent.ts:457` 注释点名「三英战吕布」→ 吕布）也从源头消失。

注入视图示意（服务端拼接，语料文本本身不含这些标记）：

```
【已检索到的《三国演义》原文片段】
[片段1] 瑾曰：“特来求结两家之好…请君侯思之。”云长勃然大怒曰：“吾虎女安肯嫁犬子乎！…”
```

模型输出（**只有结论 + 字标**，约 20~30 字）：

```
关羽拒绝了孙权的联姻，回以[片段1]。
```

服务端渲染后（**展示给用户的最终答案**；`citations[1]` 为该片段整段原文 + 出处，卡片展示）：

```
关羽拒绝了孙权的联姻，回以「吾虎女安肯嫁犬子乎！不看汝弟之面，立斩汝首！再休多言！」¹
```

### 6.4 运行期流程与兜底

| 步骤 | 执行方 | 说明 |
|---|---|---|
| 1 | 服务端 | 召回 chunks，按预算取片段，拼注入视图（纯原文 + `[片段N]` 字标） |
| 2 | 模型 | 只输出「结论 + 字标」，不输出原文、不输出出处 |
| 3 | 服务端 | 校验字标 ∈ 注入片段集合；按字标把整段原文填入 `citations`，answer 剥离字标（无角标） |
| 4 | 服务端 | 字标缺失/越界 → 走既有兜底：`buildFallback()` 已实现「原文片段 + 出处 + 一句结论」 |

**校验调整**：

- 格式校验由「必须含 `「…」（出处：第X回…）`」改为「**必须含合法字标**（字标 ∈ 本次注入的片段编号集合）」；字标非法即走兜底。
- **断言人物 ⊆ 召回人物的硬校验不受影响**：扫描对象是答案正文里的人名（`agent.ts:458`），结论里的名字照样扫。
- **顺带清理孤儿代码**：`agent.ts:459` 剥离 `（出处：…）` 的逻辑，是为「回目可能含他人名」而写；出处不进模型输出后成为死代码，应删除。

### 6.5 附带收益

- **省输出 token**：单条引用省 78 字（94%），见 §6.2；输出侧是成本更高的一侧。
- **原文逐字可信**：引用原文来自条目字段而非模型复述，**不存在抄错、漏字、改字**——这是「只给原文怎么说」这条产品承诺的直接兑现。
- **出处不可能编错**：回号与回目由字段渲染，模型没有机会把第 73 回写成第 75 回。
- **省注入字数**：现状出处头均 34 字/片段（p50 34、max 37，含回目与段号），top3 省约 102 字（对 750~1000 字预算约 10~14%）。
- **杜绝回目污染断言扫描**（§6.3 第 5 点）。
