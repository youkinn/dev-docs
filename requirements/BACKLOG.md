## 使用规则

1. 有想法先进这里，只记**场景**，不先记技术。
2. 写不出验收标准的不立项，继续留在池子里。
3. 立项时状态改为「已立项 feat-XXXX」，内容搬进独立需求文档（需求只有一份）。
4. 否掉的想法标「搁置」并写明理由，不删除，避免重复讨论。

## 筛选原则：发现场景 → 选技术

> 2026-09-16 负责人认可此口径；是否写入 `AGENTS.md` 待确认（见文末）。

- **场景优先**：先有「用户自发想用」的场景，再选技术。不为了用某个概念去造场景。
- **自然度**：需要向用户解释才用得起来的能力，自然度低，降级处理。
- **可退化**：每个方向都要有「最小一版」的交付路径，避免一上来就上重技术。
- **可验收**：写不出验收标准 → 不立项。

背景：风云三国问答最初的目的是走通大模型整套工作流（模型调用 → 工具路由 → 检索 → 可扩展），这个目的本身成立；但要选对落地场景，避免「为了用而用」。

## 详细条目

### P0 交互债（成本低、见效快、不引入新概念）

#### BL-001 随机一题按钮化

- **场景**：随机一题要先手输「随便一题」才出题，看答案要输「答案」，答题选项 A/B/C/D 也要手打。
- **自然度**：高。游戏里答题时用户不想打字。
- **技术对齐**：无（纯交互）。但它是 A003 已写下的边界声明的直接推论——**有固定参数形状的确定性能力，必须给显式入口**。
- **最小版本**：输入区加「出题 / 下一题 / 看答案」按钮 + 选项按钮。
- **成本**：仅 mcp-web。`POST /api/sango/random` 已存在，**不动契约**。
- **顺带**：统一文案。前端叫「随便一题」、后端认「随机一题 / 来一题」（A003 遗留②）。

#### BL-002 天气快捷输入

- **场景**：查天气每次手打城市名。
- **自然度**：中。有「最近用过的城市」会顺手很多。
- **最小版本**：前端本地存最近城市，做成快捷按钮。
- **成本**：仅 mcp-web。

#### BL-003 错误信封补齐

- **场景**：请求体非法 JSON 或超过 32kb 时返回的是 express 默认 HTML，不是 `{code, data, message}`（A001 起即存在，A003 遗留③）。
- **自然度**：低（用户无感），但属**契约完整性**。
- **成本**：mcp-orchestrator，小。可并入下一个后端特性，不必单独立号。

### 场景候选（按自然度排序）

#### BL-010 截图问答　← 最推荐的新功能

- **场景**：玩家在游戏里遇到招募题，**截图上传 → 识别题干 → 直接给答案**。
- **自然度**：高。游戏内截图比打字快，不需要教育用户。
- **技术对齐**：多模态识别 + RAG 召回 + 结构化输出，一次吃到三个概念，且是单一闭环。
- **最小版本（可退化）**：先只做「图片 → OCR 出题干」→ 复用现有 `sango_query` 链路；识别质量不够再上多模态。
- **成本**：mcp-web（上传）+ mcp-orchestrator（新入参）；`/api/chat` 需扩展入参，**属契约变更，接口文档先行**。
- **风险**：图片体积 / 格式校验、视觉模型调用成本、识别错题导致串答案。

#### BL-011 攻略知识库（RAG）

- **场景**：风云三国里除了招将答题，还有兵种 / 装备 / 攻城等攻略问题，现在答不了。
- **自然度**：中高。玩家确实会问，但**语料从哪来是主要成本**。
- **技术对齐**：向量检索（embedding）+ Rerank + 引用来源。现有 `sango_query` 已是完整 RAG 雏形，**换召回层即闭环**，是最省力的 RAG 踩点路径。
- **最小版本**：只把召回层从 bigram 换成 embedding，仍只覆盖现有 88 题题库，先验证召回质量。
- **成本**：mcp-orchestrator 新依赖（embedding 服务或本地模型）；题库 / 语料需扩充。
- **注意**：**不是「为了用 RAG 而造知识库」。** 触发条件是题库规模涨到 bigram 不够用，或确有可用攻略语料；语料来源没解决前不立项。

#### BL-012 答题连测 + 错题本

- **场景**：一次只出一道题，答完要重新手输；答错的题没法复习。
- **自然度**：高。想练题的玩家会连着做。
- **技术对齐**：会话状态 + 多轮记忆 + 简单数据沉淀。A001 / A002 明确不做记忆，是因为当时没有需要记忆的场景——**这里才有**。
- **最小版本**：判题后自动出下一题 + 内存里记连对数。
- **成本**：mcp-web + mcp-orchestrator。要做持久化错题本需引入存储（当前会话是单实例内存、TTL 30 分钟）。

#### BL-013 出题机（LLM 造题）

- **场景**：题库 88 题，靠人手补太慢。
- **自然度**：低——**面向我们而不是面向用户**，是内部工具。
- **技术对齐**：结构化输出 / JSON schema 校验 + 生成质量评估 + 人工抽审。
- **最小版本**：一个脚本，按武将或主题生成候选题 → schema 校验 → 落成待审 JSON。
- **成本**：mcp-orchestrator 或独立脚本，无前端。
- **顺带价值**：为将来可能的微调攒 SFT 数据（见 BL-030）。

#### BL-014 流式输出（SSE）

- **场景**：现在一次性返回，长回答等待感强。
- **自然度**：中。用户不一定主动提，但体验确实更好。
- **技术对齐**：流式协议、前端增量渲染、流中途出错的处理。
- **成本**：mcp-orchestrator + mcp-web。**会改 `/api/chat` 的响应形态，属契约变更。**
- **备注**：建议等 mcp-web 有测试设施后再做（该项目目前无组件测试设施，A002 遗留待决策）。

#### BL-015 路由评测基建

- **场景**：A003 落地后，「模型到底有没有选对工具」只能靠固定问题集人工跑（A003 遗留④）。
- **自然度**：低——内部工具。
- **技术对齐**：评估集建设、LLM-as-judge、回归统计、命中率看板。
- **最小版本**：固定问题集 + 期望工具名的 JSON + 一个统计脚本。
- **成本**：mcp-orchestrator 的 scripts / test。真实 LLM 调用有成本，需限次数。
- **价值**：**后续所有特性的公共底座**，工具变多后尤其必要。

#### BL-016 名著解读：三国演义（单口径，只解读不评论）

- **场景**：三国迷问演义里的情节，要的是「原文怎么说」，不是模型的印象。风云三国旁单开「三国演义」标签，此标签下只讨论演义；三国志同构，本期不做（演义受众更广）。
- **明确非目标**：不做演义 / 正史对比，不评价谁对谁错，不做文学批评。标签之间**物理隔离**，防串味。
- **技术对齐**：语义检索召回原文 → 原文喂模型 → 模型只做归纳。用原文约束生成，目标是**减少幻觉**。
- **自然度**：中高。受众是三国迷，不是全部游戏用户。
- **语料**：演义毛本约 64 万字 ≈ 百万 token 级。embedding 一次性成本元级，**开销可忽略**。
- **最小版本（可退化）**：只上《演义》一本；现代白话问句 → hybrid 召回（BM25 + 向量）→ 渲染原文 + 出处（回目）。先不做 query 改写、先不做 rerank。
- **不做**：不上专用向量数据库。千级 chunk 用 sqlite-vec / 内存余弦足够。
- **必须钉死的边界**：模型只能给「原文直接支持的结论」并附出处；原文没提到的必须答「演义中未涉及」，**不允许用先验补全**。**拒答能力是验收核心**，比多答对一题重要。
- **最大风险**：模型的预训练记忆里混着影视剧 / 游戏 / 二创 / 三国志。即使喂了原文，仍可能按记忆回答、把原文引用当装饰。**测试必须含负样本**（演义里没有、影视剧里有的桥段），看它会不会编。
- **半文言难点（拆三层，别当成一个整体）**：① 字面层——人名 / 字 / 号 / 官爵 / 地名一对多（关羽 / 关云长 / 关公 / 汉寿亭侯），靠混合检索 + 别名表兜底；别名表是**封闭集合，属数据整理，不是 NLP 难题**；② 语义层——现代白话问法 ↔ 半文言表达，靠向量 + 可选 query 改写；③ 篇章层——一事横跨多回（三顾茅庐跨 37–38 回），靠召回条数 + 回目邻接扩展。
- **版本**：固定毛本，避免毛本 / 嘉靖壬午本的文字与回目差异。注意**正文公版 ≠ 现代点校排印本公版**，需用公版文字自行标点。
- **预留**：数据结构与工具名保留 `source` 维度，二期接《三国志》只换语料，不改契约。
- **立项前**：20–30 个现代白话问句 + 若干负样本的召回探针，拿命中率与引用忠实度说话（不立号、不动线上契约）。
- **探针 A（2026-09-16 实跑，H2 忠实度）**：**未通过**。投毒第五回问「斩华雄的是谁」，6 次全部答「关羽」（5 次把语料里的「张三」合理化当成关羽的别名，1 次纯记忆），工具调用率 6/6；对照组 A1（原文）与负样本 A3（电影 / 正史桥段）均通过。→ 按生死线**停 T3（H1 召回探针）**，等负责人决策：① 投毒设计重做再测；② prompt 加「人名以原文为准」约束再测；③ 产品降级为原文直出（不生成答案）。
- **需求变更（2026-09-16，Coco）**：检索层落点由「orchestrator 本地工具」改为 **MCP 工具**（见 `docs/sango-classics-rag-research.md` §3 D1）。设计：MCP 检索工具**只收一个入参**，系统据此确定本次会话上下文（source / domain）→ 调整提示词 → 交大模型处理，**大模型调度 MCP 工具**；为二期接《三国志》、重构风云三国铺路——换语料 / 换场景只换入参与语料，不动编排骨架。
### 慎用 / 搁置

#### BL-030 微调（fine-tune）—— 搁置

- **现状**：88 题规模下 prompt + few-shot 远没到天花板；当前瓶颈是数据量与交互，不是模型能力。
- **触发条件**（三条同时满足才重新评估，避免反复讨论）：
  1. 出现「问法 → 题目 ID」这类有大量标注数据的任务；
  2. 已验证 prompt 方案在该任务上到瓶颈（有对比数据，不是感觉）；
  3. 推理成本或延迟是真实痛点。
- 不满足 → 继续搁置。
